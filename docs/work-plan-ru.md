# План реализации Bunker

Актуально на 13 ноября 2026 года. Цель — законченная браузерная экспедиция на русском языке по [ТЗ](spec/bunker_technical_spec_ru_v1.md): 17 комнат, два этажа, автономные инженерные системы, плесень, крысы, добыча, сохранение и окончательный выход либо смерть. Текущая версия баланса реализации — [1.1](../data/bunker_balance_v1_1.json), сборка 0.3.3, схема снимка 3.

Технологическая основа: TypeScript, Vite, PixiJS, HTML/CSS. Численная модель работает в Node без браузера. Настольные Chromium и Firefox, минимальное окно 1280×720. Подробные архитектурные границы описаны в [implementation-plan.md](implementation-plan.md).

## Первый рабочий пакет и оставшиеся проверки

Перечисленный пакет реализован, проверен и расширен инженерными модулями этапа 3. Численное ядро запускается локально; браузерная сборка проверена в GitHub Actions. Ниже — состав завершённого первого пакета.

1. Создать `package.json`, настройки TypeScript/Vite, lockfile и команды `dev`, `build`, `preview`, `check`, `test:sim`; подключить PixiJS и проверку схем. Добавить Vitest, перенести существующие контрольные случаи без изменения ожидаемых результатов. Playwright подключить для первых браузерных сценариев.
2. Создать единый загрузчик баланса 1.1 и исходных манифестов. Версии схемы, баланса и источников должны сохраняться явно. Исходный `docs/spec` не менять.
3. Нормализовать двери к стабильным ID; `initial_state: null` трактовать по ТЗ как открытое положение и режим «Авто». Сохранить геометрию и последовательные пары комнат. Добавить проверку ссылок и уникальности.
4. Определить `WorldState`, `ItemLocation`, `Command`, `Action` и состояния графов. Разделить истинные физические значения, сигналы датчиков и сведения, разрешённые игроку.
5. Реализовать и проверить PCG32 с потоками `world`, `loot`, `fungus`, `rats`, `equipment`; зафиксировать порядок ID и правила выдачи идентификаторов новым объектам.
6. Добавить секундный цикл с явными фазами A.14, постановку команд, паузу и экспорт/восстановление снимка. Сначала фазам разрешено быть пустыми: это каркас исполнения, а не готовая физика.
7. Сделать служебный экран запуска с seed, номером тика, паузой и экспортом состояния. Его диагностические сведения не переносить в обычный игровой HUD.

Критерии окончания пакета:

- [x] Сборка и проверки проходят одной последовательностью команд из README.
- [x] В мире ровно 17 комнат и корректные связи из принятой планировки.
- [x] Два запуска с одним seed/журналом команд совпадают; пауза не меняет состояние.
- [x] Сохранённый снимок восстанавливается без изменения RNG и логического времени.
- [x] Баланс 1.1 выбран явно; температурные контрольные случаи остаются зелёными.
- [x] Понятно отмечено, какие фазы ещё пусты и какие механики появятся в следующем пакете.

Проверки покрывают эталонные комнаты, лестницу, полный инженерный граф, JSON-продолжение, повтор по командам, `Session`, часы, Zod-загрузчик, IndexedDB и начальный UI. Образец спальни реализован в пределах одной освещённой комнаты. Следующий этап — переходы между комнатами, двери и общий контур обзора/света; полная приёмка инженерных действий дополнится взаимодействиями игрока и аэрозолем.

## Решения, принимаемые при реализации

Для этих задач достаточно текущего ТЗ и обычных решений разработки:

- Авторские позиции мебели, шкафов, вентилей и контейнеров; ширина проходов и препятствия. Обязательны доступ к дверям/лестницам и сохранение принятой геометрии комнат.
- Точный протокол времени команд и движения. Экологическая симуляция остаётся секундной, движение — плавным и воспроизводимым; зафиксировать поведение на границах тика, во время действия и при закрытии вкладки. Офлайн-время после загрузки не начислять.
- Отдельные маски геометрического обзора и света; общие правила для изображения, подсветки и клика по объектам. Карты и памяти видимости нет.
- Конкретные имена, даты, изображения и тексты архивных находок с единым реестром связей. Тексты насосных уже есть в пакете.

Любое расширение механик оформляется отдельно. Новая математическая неоднозначность сначала проверяется по действующему балансу и ТЗ; небольшое техническое решение фиксируется в документации и тесте. Повторно согласовывать уже заданные коэффициенты не требуется.

На каждом этапе сохраняем seed, лог команд и версию баланса для замечаний. Переход к следующему этапу опирается на проверяемый результат; полноценная художественная приёмка и проверка понимания игроком остаются отдельными задачами.
